Phase 0: Polymorphic Data Model Architecture
===============================================
Core Requirement: All entities must be connected through polymorphic relationships from a business perspective. The data model must support hierarchical spatial nesting, multi-party associations, and routine-based temporal patterns.

0.1 Polymorphic Entity Connection Framework
  - Every entity (Contact, Location, Routine, Trip, Plan) must support polymorphic references
  - Entities connect through shared spatial and temporal dimensions
  - Relationships are bidirectional and queryable from any connected node

0.2 Spatial Hierarchy (Location Polymorphism)
  - Contacts can be connected to locations at multiple granularity levels:
    * Geographic Level: lat/lng coordinates on a map
    * Building Level: structured building with unique identifier
    * Floor Level: floors within a building (e.g., Floor 1, Floor 2)
    * Room Level: rooms within floors (e.g., Room 101, Conference Room A)
  - A single contact can have multiple location associations (home, office, frequent visits)
  - Spatial hierarchy: Map Region → Building → Floor → Room
  - Each level inherits spatial properties and can have its own metadata

0.3 Temporal Routine Model (Trip as Routine)
  - Daily trips on the road are modeled as Routines with multi-stop patterns
  - A Routine represents a planned sequence of activities over time
  - Routine Components:
    * Multiple location stops (ordered sequence)
    * Planned duration per stop
    * Total trip duration estimate
    * Start and end time windows
    * Assigned participants (persons)
  - A single trip can have multiple persons onboard (many-to-many relationship)
  - Routines can be recurring (daily, weekly, custom schedule)

0.4 Multi-Party Associations
  - Trips/Routines can have multiple persons assigned
  - Persons (Contacts) can be assigned to multiple trips
  - Relationship supports: primary organizer, participants, observers
  - Attendance tracking per routine execution

0.5 Entity Relationship Map
  - Contact ↔ Location (many-to-many, via spatial associations)
  - Location ↔ Building (one-to-many, building contains locations)
  - Building ↔ Floor (one-to-many, floor belongs to building)
  - Floor ↔ Room (one-to-many, room belongs to floor)
  - Routine ↔ LocationStop (one-to-many, routine has multiple stops)
  - Routine ↔ Person/Contact (many-to-many, routine has multiple participants)
  - Trip ↔ Plan (one-to-one or one-to-many, trip may have associated plans)

0.6 Cost Model (v4.0 Financial Polymorphism)
  - Every entity supports cost tracking for financial management
  - Cost Categories:
    * Trip Cost: total budget, actual spending, currency, breakdown by category
    * Routine Cost: per-routine budget, execution cost, recurring expenses
    * Floor Cost: maintenance cost, utility cost, rental/lease cost
    * Room Cost: equipment cost, setup cost, per-use cost
    * Contact Cost: living cost, support cost, compensation
    * Contact Cost Breakdown: housing, food, transport, health, education, entertainment

0.7 Event Taxonomy (v4.0 External Events)
  - Calendar supports multiple event types with distinct visual representations
  - Event Types:
    * Routine Events: linked to user routines, recurring patterns
    * External Events: third-party events imported or manually added
    * Activities: personal activities with duration and location
    * International Events: global holidays, cultural celebrations

Polymorphic Connection Guidelines
==================================
1. Every entity must have at least one connection point to another entity type
2. Location hierarchy is universal: Map → Building → Floor → Room
3. Contacts connect to locations via locationAssociations array
4. Routines/Trips connect to locations via locationStops array
5. Routines/Trips connect to persons via assignedPersons array
6. Plans connect to routines via routineId reference
7. All connections are bidirectional and queryable
8. Deletion of an entity must cascade or prompt for orphaned connection handling
9. Cost data rolls up through entity hierarchy (room → floor → building)
10. Calendar events connect to routines, contacts, and locations
11. Maturity scores are calculated from entity data (cost, health, skills)

7.1 Core Concept: Four Stages of Competence
-------------------------------------------
Stage 1: SENSING (Unconscious Incompetence → Awareness)
  - Goal: Surface unmonitored life metrics without active effort from user
  - Current Coverage: ✅ Highcharts Baseline, ✅ Telemetry Signal Engine, ✅ Open Map
  - Gap: No automatic detection of "life metrics" or "energy leaks"
  - Enhancement: Add passive data ingestion from device sensors, calendar, and utilities

  - Goal: Create cognitive friction highlighting reality vs goals
  - Current Coverage: ✅ Maturity Assistant (Likert scale), ✅ Personal Risk Table, ✅ Capabilities Canvas
  - Gap: No radar overlay comparing current vs target baselines
  - Enhancement: Add "Prefrontal Friction" visualization showing gap magnitude

Stage 3: ORCHESTRATION (Conscious Competence → Deliberate Practice)
  - Goal: Structured execution workbench for habit building
  - Current Coverage: ✅ BPMN.js Workflow (routineView.js), ✅ Kanban/Gantt, ✅ FullCalendar
  - Gap: No "Synaptic Myelination" tracking (repetition consistency metrics)
  - Enhancement: Add streak tracking, consistency heatmaps, neural pathway visualization

Stage 4: AUTOMATED TWIN (Unconscious Competence → Basal Ganglia Automation)
  - Goal: Frictionless automated baseline operation
  - Current Coverage: ✅ SignalR Auto-Alerts, ✅ OrgChart Kinship Badges
  - Gap: No "Executive Dashboard" for whole-family oversight
  - Enhancement: Add automated exception handling, predictive alerts, cultural co-regulation

PART VIII: RISK ASSESSMENT

Technical Risks:
- Device sensor API compatibility across browsers
- SignalR real-time connection stability
- Performance impact of real-time panel updates
- localStorage size limits with expanded data model

Mitigation Strategies:
- Feature detection + graceful degradation for sensor APIs
- WebSocket fallback to polling if SignalR fails
- Debounced panel updates, virtual scrolling for large datasets
- IndexedDB migration plan for storage overflow
