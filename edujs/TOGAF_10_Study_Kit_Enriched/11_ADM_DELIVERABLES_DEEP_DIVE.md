# 11. ADM Deliverables Deep Dive

This chapter is an exam-focused synthesis of the typical deliverable baseline. Deliverables are tailored; do not assume every engagement creates every item at maximum detail.

## Phase-to-deliverable map

- **Preliminary:** Tailored Architecture Framework, Organizational Model for EA, Architecture Principles, business goals/drivers restatement, Request for Architecture Work.
- **A:** Statement of Architecture Work, Architecture Vision, Communications Plan, Capability Assessment, initial Architecture Definition Document.
- **B/C/D:** Architecture Definition Document, Architecture Requirements Specification, candidate Architecture Roadmap components, ABBs.
- **E:** updated Definition Document, Roadmap, SBBs, draft Implementation and Migration Plan, Transition Architectures, initial governance planning.
- **F:** finalized Roadmap, detailed Implementation and Migration Plan, finalized Transition Architectures, Implementation Governance Model.
- **G:** Architecture Contract, Change Requests, Compliance Assessments.
- **H:** governance/contract/compliance updates, Change Requests, Request for Architecture Work, Requirements Impact Assessment.
- **Requirements Management:** Requirements Specification and Requirements Impact Assessments throughout.

## Tailored Architecture Framework

Tailor first to the enterprise, then to the specific Architecture Project. Typical content: tailored method; tailored deliverables/artifacts; configured tools; terminology/presentation conventions; and interfaces with corporate planning, portfolio/program/project management, engineering/development, operations, and governance.

## Organizational Model for EA

Typical content: impacted scope, maturity gaps and improvement approach, roles/responsibilities, constraints, budget, governance, and support strategy. Be explicit about boundaries and governance relationships between architecture practitioners.

## Request for Architecture Work

Sponsor-triggered high-level request that initiates a cycle. It includes sponsor/mission, goals, strategic plans, time limits, environmental changes, constraints, budget, current business/IT descriptions, developing organization, and available resources. It may also result from approved changes or migration planning.

## Statement of Architecture Work

Phase A's contract-like response to the request. It includes background, description/scope, overview of Vision, scope-change procedures, roles, deliverables, acceptance, plan/schedule, and approvals.

## Architecture Vision

High-level summary of enterprise change and desired outcome, used to agree direction and focus detailed feasibility work. Include problem, stakeholders/concerns, issues/scenarios, objectives, summary domain views, mapped requirements, and reference to the draft Definition Document.

## Communications Plan

Identify stakeholder groups, needs, key messages, communication risks and success factors, channels/repository access, timetable, location, and ownership.

## Capability Assessment

Assess:

- business capability baseline/target performance and realization;
- IT change/operation maturity, capacity, and organizational impact;
- architecture governance, skills, repository landscape, standards, reference models, and reuse potential;
- transformation readiness factors, current/target ratings, and risks.

## Architecture Definition Document

Qualitative description of architectural intent across Business, Data, Application, and Technology domains and Baseline, Transition, and Target states. Include scope, objectives, constraints, principles, models/views, rationale, mappings to landscape/reference models/standards, reuse assessment, gaps, impacts, and transitions.

## Architecture Requirements Specification

Quantitative and testable statements for implementation conformance. Include success measures, architecture requirements, service contracts, implementation guidance/specifications/standards, interoperability, service management, constraints, and assumptions.

**Exam contrast:** Definition Document explains what the architecture is and intends; Requirements Specification states measurable criteria implementation must satisfy.

## Architecture Roadmap

Timeline of work packages progressing from Baseline to Target, with business value and transitions. Include work package descriptions, requirements, dependencies, relationship to opportunity and architecture documents, value, implementation factors, consolidated gaps/solutions/dependencies, Transition Architectures, risks, recommendations, and SBBs.

## Implementation and Migration Plan

Executable change schedule grouped into portfolios/programs/projects. Include strategy and sequence, work package allocation, capabilities, milestones, work breakdown, portfolio impacts, charters, value, risks/issues/assumptions/dependencies, resources/cost, benefits, and migration-option costs.

## Transition Architecture

Formal architecturally significant intermediate state. Describe Business, Data, Application, and Technology Architecture for each transition state.

## Implementation Governance Model

Project-specific path into Phase G governance: processes, structure, roles/responsibilities, checkpoints, and success/failure criteria.

## Change Request

Includes proposed change, rationale, impact, affected requirements and priorities, phases to revisit, phase leading reprioritization, investigation results, recommendations, and repository reference.

## Requirements Impact Assessment

Assesses how new information changes requirements and architecture. It normally references specific requirements, priorities, phases requiring revisit, reprioritization ownership, results, recommendations, and repository identifiers.
